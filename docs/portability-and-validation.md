# Портируемость, безопасность SSE и валидация hostname

Три независимых изменения, вошедших в одну сборку. Все направлены на то,
чтобы панель работала предсказуемее на большем числе дистрибутивов и не
протекала чувствительными данными наружу.

---

## 1. Пути системных бинарников больше не захардкожены

### Что было

Раньше панель искала внешние программы строго по абсолютным путям:

| Бинарник | Хардкод |
|---|---|
| `dnsmasq` | `/usr/bin/dnsmasq` |
| `sudo` | `/usr/bin/sudo` |
| `systemctl` | `/usr/bin/systemctl` |
| `service` (sysvinit) | `/usr/sbin/service` |
| `rc-service` (OpenRC) | `/usr/bin/rc-service` |
| `sv` (runit) | `/usr/bin/sv` |

На **Alpine**, **Debian до usrmerge**, **Devuan** и embedded-сборках, где
эти файлы лежат в `/bin` или `/sbin`, панель сообщала, что init-система не
обнаружена, а `dnsmasq --test` молча падал — без видимой причины.

### Что стало

Поиск каждого бинарника идёт в три шага:

1. **`$PATH`** (через `exec.LookPath`) — учитывает реальную переменную
   окружения процесса, работает на любом дистрибутиве из коробки.
2. **Fallback по списку абсолютных путей** — `/usr/bin`, `/usr/sbin`, `/bin`,
   `/sbin` в порядке предпочтения.
3. **Флаг-override** — оператор может явно указать путь при запуске.

### Новые флаги

Все опциональны, по умолчанию пусты (включён авто-резолв):

| Флаг | По умолчанию ищет |
|---|---|
| `-dnsmasq-bin` | `dnsmasq` |
| `-sudo-bin` | `sudo` |
| `-systemctl-bin` | `systemctl` |
| `-service-bin` | `service` |
| `-rc-service-bin` | `rc-service` |
| `-sv-bin` | `sv` |

Пример использования (Alpine, нестандартный путь к dnsmasq):

```bash
intermasq -dnsmasq-bin /usr/local/sbin/dnsmasq
```

### Что это меняет для оператора

- **Ничего, если у вас стандартный Linux с systemd.** Резолв найдёт те же
  файлы по тем же путям.
- **Alpine / Void / Devuan теперь работают без патча исходников.**
- При отсутствии `dnsmasq` панель напечатает в stderr предупреждение:
  `[BINS] dnsmasq binary not found; 'dnsmasq --test' pre-checks will fail` —
  больше не нужно гадать, почему валидация конфига не работает.

## 2. SSE-токен передаётся через заголовок, а не в URL

### Что было

Server-Sent Events (поток `arp` и `dnsmasq_status` в реальном времени)
авторизовался через query-параметр:

```
GET /api/events?token=eyJhbGciOiJIUzI1NiIs...
```

Токен попадал:
- в access-логи nginx/Apache/Caddy перед панелью,
- в логи самой панели (если включены),
- в `Referer`-заголовок, если пользователь уходил с вкладки,
- в историю браузера.

Любой, кто читал логи, получал действительный JWT на 72 часа.

### Что стало

Токен передаётся в стандартном заголовке `Authorization: Bearer ...`. URL
выглядит чисто: `GET /api/events`.

Под капотом:
- Фронтенд использует библиотеку
  [`event-source-polyfill`](https://www.npmjs.com/package/event-source-polyfill)
  вместо нативного `EventSource`. Нативный API не позволяет ставить
  произвольные заголовки — это ограничение стандарта W3C, поэтому
  понадобится polyfill.
- `authMiddleware` больше не принимает `?token=` для `/api/*` — только
  заголовок `Authorization` или `X-API-Key`.

### Исключение: `/metrics`

Эндпоинт Prometheus-метрик `GET /metrics?token=...` **по-прежнему принимает
query-токен**. Конфиг scrape в Prometheus не позволяет задавать кастомные
заголовки без sidecar'а, поэтому `?token=` здесь остаётся как
обоснованное исключение. См. `docs/metrics.md` (если есть) или комментарий
в `metrics.go:checkMetricsAuth`.

### Что это меняет для оператора

- **Пользователям UI** — ничего, всё работает само.
- **Внешним скриптам, дёргающим `/api/...` через `?token=`** — перевести на
  заголовок `Authorization: Bearer <token>`.
- **Access-логи** больше не содержат JWT.

## 3. Имена хостов валидируются по DNS RFC

### Что было

```go
hostnameRegex = regexp.MustCompile(`^[a-zA-Z0-9-.]+$`)
```

Пропускал всё, что состоит из букв, цифр, дефисов и точек в любом порядке:
`-host`, `host.`, `host..name`, `host_name` (последнее, впрочем, уже
отвергалось — underscore не в классе), `.`. dnsmasq такое принимает, но
многие DNS-клиенты и резолверы обрабатывают непредсказуемо.

### Что стало

Имя проходит проверку по **RFC 952 / RFC 1123 / RFC 1034**:

- Каждый label (часть между точками) — **1–63 символа**.
- Label начинается и заканчивается **буквенно-цифровым** символом.
- Внутри label'а допустимы буквы, цифры и дефис.
- Label'ы разделены **ровно одной точкой**.
- Общая длина имени — **≤253 символа**.

Регулярка:

```
^[a-zA-Z0-9]([a-zA-Z0-9-]{0,61}[a-zA-Z0-9])?(\.[a-zA-Z0-9]([a-zA-Z0-9-]{0,61}[a-zA-Z0-9])?)*$
```

### Примеры

| Имя | Статус | Почему |
|---|---|---|
| `nas` | ✓ | один label |
| `nas.lan` | ✓ | два label'а |
| `my-server` | ✓ | дефис внутри |
| `1host` | ✓ | RFC 1123 разрешил ведущую цифру |
| `a-b-c.example.local` | ✓ | несколько label'ов с дефисами |
| `-host` | ✗ | ведущий дефис |
| `host-` | ✗ | замыкающий дефис |
| `.host` | ✗ | ведущая точка |
| `host.` | ✗ | замыкающая точка |
| `host..lan` | ✗ | пустой label между точками |
| `host name` | ✗ | пробел |
| (строка длиннее 253 символов) | ✗ | превышен лимит |

### Что это меняет для оператора

- **Существующие конфиги продолжают читаться.** Парсер `dhcp-host=` не
  валидирует hostname при чтении — невалидные имена в уже сохранённых файлах
  отображаются и работают.
- **Повторное сохранение невалидного имени отклоняется.** При попытке
  добавить или отредактировать хост с именем вроде `-server` панель вернёт
  `400 invalid_hostname` / `400 invalid_data`. CSV-импорт такие строки
  пропустит (как и раньше пропускал строки с неверным MAC/IP).
- **Перед массовым обновлением** имеет смысл прогнать свои `.conf`-файлы
  через что-то вроде:
  ```bash
  grep -E 'dhcp-host=.*,-[a-zA-Z0-9]|dhcp-host=.*[a-zA-Z0-9]-,' /etc/dnsmasq.d/*.conf
  ```
  чтобы найти потенциально проблемные записи.
