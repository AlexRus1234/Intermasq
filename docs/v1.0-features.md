# Новые возможности Intermasq v1.0

Закрывающий рывок к версии 1.0. Добавлены: observability через `/metrics`,
DHCP-теги на статических хостах, структурированные редакторы `dhcp-option` и
`server=/domain/upstream`, поддержка PXE-директив, объединённый flow
«Обнаружение» и консолидированная вкладка «Безопасность». Также закрыт
security-блокер с fallback signing key.

Подробное описание — ниже. Сопутствующий файл с конкретными правками:
`логи/v1.0-push-session.md`.

---

## 1. Security: обязательный `INTERMASQ_SECRET`

Раньше при отсутствии `INTERMASQ_SECRET` процесс молча подставлял
`"default-secret"` как HMAC-ключ для JWT. Любой, кто прочитал исходники, мог
кушать валидные токены с любым `sub` и получать полный admin-доступ.

Теперь:

- Если `INTERMASQ_SECRET` не задана, процесс **падает при старте** с понятной
  ошибкой в stderr и подсказкой `openssl rand -hex 32`.
- Существующие деплои должны прописать переменную окружения в systemd-юните
  (например `Environment="INTERMASQ_SECRET=<hex>"`) или export'нуть её в shell.

```ini
# /etc/systemd/system/intermasq.service.d/override.conf
[Service]
Environment="INTERMASQ_SECRET=3f5c8a2b..."
```

`api-key` (через заголовок `X-API-Key`) для плагинов остаётся как был — это и
есть `INTERMASQ_SECRET`, теперь просто гарантированно непредсказуемый.

## 2. Observability: `/metrics` для Prometheus

Новый endpoint в exposition-формате. Один process-scrape даёт полную картину
работы панели и здоровья dnsmasq.

### Endpoint

```
GET /metrics?token=<INTERMASQ_SECRET>
# либо Authorization: Bearer <JWT>
# либо X-API-Key: <INTERMASQ_SECRET>
```

`/metrics` живёт **вне** группы `/api`, чтобы URL соответствовал конвенции
Prometheus (`http://host:8081/metrics`). Аутентификация — на выбор: Bearer JWT,
`X-API-Key`, или `?token=<jwt-или-secret>` (последнее удобно для
`scrape_config`, т.к. без extras Prometheus не умеет кастомные заголовки).

### Метрики

| Метрика | Тип | Описание |
|---|---|---|
| `intermasq_hosts_total` | gauge | Кол-во управляемых dhcp-host записей |
| `intermasq_leases_active` | gauge | Текущее кол-во активных DHCP-аренд |
| `intermasq_arp_online_total` | gauge | Кол-во устройств, помеченных онлайн по ARP |
| `intermasq_dnsmasq_active` | gauge | 1, если unit dnsmasq активен, иначе 0 |
| `intermasq_reloads_total` | gauge | Кол-во успешных reload'ов, инициированных панелью |
| `intermasq_dnsmasq_test_failures_total` | gauge | Сколько раз `dnsmasq --test` отклонил изменение |
| `intermasq_uptime_seconds` | gauge | Seconds since process start |
| `intermasq_domain_up{domain=…}` | gauge | 1, если домен резолвится, иначе 0 |
| `intermasq_domain_resolve_seconds{domain=…}` | gauge | Latency последнего резолва |

`*_total` сейчас gauge, а не counter — в планах на рефакторинг перевести в
настоящие counter'ы (`promauto`), пока что достаточно простых atomic-интов без
внешних зависимостей.

### DNS health-check

Фоновая горутина (`startDNSHealthChecker`) раз в 60 секунд резолвит каждый
домен из управляемых DNS-записей (`address=`/`cname=`) через `net.Resolver` с
таймаутом 3 секунды. Результат кешируется в памяти и читается в `/metrics`.

В Grafana или Alertmanager элементарно строится алерт «домен упал»:

```promql
intermasq_domain_up{domain="wiki.lan"} == 0
```

### Пример scrape_config

```yaml
scrape_configs:
  - job_name: intermasq
    scrape_interval: 30s
    metrics_path: /metrics
    params:
      token: ['3f5c8a2b...']  # INTERMASQ_SECRET
    static_configs:
      - targets: ['172.20.0.1:8081']
```

### Механизм (`metrics.go`)

- `metricsCounters{Reloads, TestFailures atomic.Int64, StartedAt time.Time}` —
  инкрементится из `reloadDnsmasq` и всех вызовов `dnsmasq --test`.
- `dnsHealth` map + RWMutex; `runDNSHealthPass()` обходит `readAllAliases()`.
- `writeSimpleMetric` / `writeLabeledMetric` — форматирование в exposition.

## 3. DHCP-теги на статических хостах

dnsmasq позволяет помечать хост тегом (`set:iot`) и затем применять к нему
опции по совпадению (`dhcp-option=tag:iot,option:router,10.0.0.1`). Раньше
парсер это молча съедал в поле hostname. Теперь теги — полноценное поле
модели.

### Что появилось

- Поле `tags []string` в `HostEntry` (json: `tags,omitempty`).
- В форме «Статика» — поле ввода назначаемых тегов (comma-separated):
  `set:iot,set:guest`. С подсказкой и tooltip'ом.
- В таблице хостов — колонка «Tags» с бейджами.
- Теги участвуют в полнотекстовом поиске.
- Bulk-move и bulk-edit **сохраняют** теги (раньше терялись).
- Валидация на форме: regex `(set|tag|id):[a-zA-Z0-9_][a-zA-Z0-9_-]*`.
- `id:<client-id>` принимается ради round-trip, но не выносится в UI как
  отдельное поле.

### Сериализация

dnsmasq-строка строится как `dhcp-host=mac,hostname,ip[,tags…]`. Порядок тегов
последний — это конвенция примеров dnsmasq и удобнее для diff'а.

```
dhcp-host=aa:bb:cc:dd:ee:ff,nas,10.0.0.5,set:iot,set:vlan10
```

### Механизм

- `parseDhcpHostLine(raw, file) (HostEntry, bool)` — единый канонический
  парсер. Заменил 5 дублированных inline-парсеров в `dnsmasq.go`/`handlers.go`.
- `formatDhcpHostLine(h HostEntry) string` — обратная сериализация.
- `validateHostTags` / `normalizeHostTags` — в `handlers.go`.

## 4. Структурированный редактор `dhcp-option`

`dhcp-option` — самая частая DHCP-директива после `dhcp-host` (gateway, DNS,
NTP, broadcast и т.д.). Раньше редактировалась как свободный текст (`type:
'list'`). Теперь — визуальная форма с пресетами.

### Что появилось

- Новый тип `dhcpoption` в `directives.js`.
- Пресеты для 10 частых опций: `option:router`, `option:dns-server`,
  `option:domain`, `option:broadcast`, `option:ntp-server`,
  `option:netbios-ns`, `option:netbios-scope`, `option:vendor-class`,
  `option:tftp-server`, `option:bootfile-name` — с номерами RFC 2132 и
  плейсхолдерами значений.
- Компонент `DhcpOptionRow.vue` с тремя полями: тег (`set:tag:`/`tag:tag:`
  опционально), селект опции (или custom), значение.
- Числовой формат (`3,192.168.1.1`) распознаётся и мапится на именованный
  пресет, если номер известен.

### Принятые формы

```
dhcp-option=option:router,192.168.1.1
dhcp-option=tag:iot,option:dns-server,1.1.1.1
dhcp-option=3,192.168.1.1                       # numeric, маппится на router
dhcp-option=option:ntp-server,192.168.1.1,time.cloudflare.com
```

### Механизм (`DhcpOptionRow.vue`)

- `parseInto(target, raw)` — разбор `[tag:]option,value` в три поля.
- `onPresetChange()` — сбрасывает customOption при выборе пресета из списка.
- watch на `directive.value` с round-trip guard — не затирает форму при вводе.

## 5. Forwarding-правила (`server=/domain/upstream`)

`server` — основная директива маршрутизации DNS: «отдай `*.corp` на внутренний
резолвер», «забудь глобальный upstream». Раньше поле было свободным текстом.

### Что появилось

- Новый тип `forwarding` в `directives.js`.
- Компонент `ForwardingRow.vue` с двумя полями: домен (в слэшах) и upstream.

### Принятые формы

```
server=/corp/10.0.0.53          # перечислять *.corp через 10.0.0.53
server=/.corp/10.0.0.53         # wildcard по суффиксу
server=8.8.8.8                  # глобальный upstream (поле domain пустое)
server=/blocked.local/#         # не форвардить (drop)
```

## 6. Поддержка PXE / netboot

dnsmasq массово используется для сетевой загрузки (Proxmox auto-install,
diskless, тонкие клиенты). Раньше PXE-директивы не были видны в редакторе
конфигурации.

### Что появилось

- Новая визуальная группа **«PXE / Сетевая загрузка»** (`groupPxe`) в
  редакторе конфигурации, между DHCP и Logging.
- Директивы: `dhcp-boot`, `dhcp-match`, `dhcp-mac`, `pxe-service`, `pxe-prompt`.
  Редактируются как `list`/`string` (свободный текст) — формат PXE-директив
  слишком вариативен, чтобы загонять их в визуальную форму без потери общности.

### Пример

```
dhcp-match=set:efi-x86_64,option:client-arch,7
dhcp-boot=tag:efi-x86_64,syslinux.efi
pxe-service=tag:efi-x86_64,X86-64_EFI,syslinux.efi
```

## 7. Вкладка «🔍 Обнаружение» (Discovery)

Раньше leases, new-devices и lease-to-static были размазаны по двум вкладкам и
двум разным кнопкам. Теперь это один flow.

### Что в одной вкладке

- **Секция 1: «Неизвестные устройства (ARP, не настроены)»** — список MAC из
  ARP-таблицы, которых нет ни в static, ни в leases. С OUI-lookup'ом вендора.
  Кнопка «➕ Добавить в статику» переключает на вкладку Static с
  предзаполненной формой.
- **Секция 2: «Новые DHCP-аренды»** — leases, у которых MAC не в static.
  Чекбоксы для bulk-to-static (кнопка «➕ Добавить N в статику»), кнопка
  «➕ В статику» на каждой строке, индикатор ARP-онлайна.

### Что исчезло из верхнего таб-бара

Ушли отдельные вкладки «Аренды» и «Новые устройства». Старые компоненты
(`LeasesTab.vue`, `NewDevicesTab.vue`) физически не удалены — на случай
обратной совместимости и для переиспользования в будущих отчётах.

## 8. Вкладка «🛡️ Безопасность» (Safety)

Пять safety-механизмов (rollback `.bak`, versioned history с diff, ZIP
backup/restore, audit-log, templates) раньше жили в разных углах UI. Теперь
три из них собраны в одной вкладке для быстрого доступа.

### Что в одной вкладке

- **Backup & Restore** — скачать ZIP всех `.conf`, восстановить ZIP с
  pre-flight `dnsmasq --test` и авто-бэкапом текущих файлов как `.restore.bak`.
- **Templates** — список сохранённых шаблонов hostname/IP-range с кнопкой
  «⚙️ Управлять» (открывает модалку создания/удаления).
- **Audit log** — переиспользует `AuditTab`, без изменений в его логике.

History (versioned) остался контекстным модальным окном в трёх вкладках
(Static, DNS, Config) — это правильно, т.к. история всегда про конкретный
файл. Rollback `⏪` остался там же.
