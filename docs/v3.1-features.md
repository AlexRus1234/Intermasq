# Новые возможности Intermasq v3.1

Четыре точечные улучшения поверх v3.0 + внутренний рефакторинг модулей.
Функциональных regressions нет — все существующие эндпоинты, форматы
запросов/ответов и поведение UI сохранены.

---

## 1. Удаление `.conf`-файла через UI

Вкладка **«Настройки dnsmasq»** получила кнопку `🗑 Удалить файл`.

### Как работает

1. Выберите файл в табах.
2. Нажмите `🗑 Удалить файл` (красная, рядом с `🕒 История` и `⏪ Откат`).
3. Confirm-диалог объясняет, что файл будет **физически удалён** из
   `-conf-dir` и подсказывает, как восстановить через history.
4. После подтверждения:
   - Текущее содержимое файла сохраняется в versioned history
     (`-history-dir`).
   - `os.Remove(file)` + `os.Remove(file + ".bak")`.
   - Пишется audit-запись `action=config_delete_file`.
   - В ответе приходит обновлённый `ConfigSnapshot` — UI сразу убирает
     таб удалённого файла.
5. Нажмите «Применить» в шапке, чтобы dnsmasq перестал загружать
   отсутствующий файл.

### Восстановление

Удалённый файл восстанавливается через стандартную модалку «🕒 История»:

1. Откройте любой **другой** `.conf`-файл в той же вкладке.
2. Нажмите `🕒 История` — увидите версии всех файлов (включая удалённый).
3. Path удалённого файла сохранён в history; выберите версию и нажмите
   `⏪ Восстановить`. Файл будет создан заново с тем же содержимым.

> History использует sha256-хэш абсолютного пути файла для именования
> версий, поэтому даже после удаления файл восстанавливается по тому же
> абсолютному пути.

### API

```http
DELETE /api/config/file
Authorization: Bearer <token>
Content-Type: application/json

{"file": "/etc/dnsmasq.d/old.conf"}
```

**Ответ 200:** обновлённый `ConfigSnapshot` (как у `POST /api/config/file`).

**Ошибки:**

| Код | error | Когда |
|-----|-------|-------|
| 400 | `invalid_data` | Неверный JSON. |
| 400 | `invalid_filename` | Имя файла не заканчивается на `.conf` или содержит `/` / `\`. |
| 403 | `access_denied` | Путь вне `-conf-dir`. |
| 404 | `file_not_found` | Файла не существует. |
| 500 | `delete_error` | Ошибка `os.Remove` (права, lock и т.д.). |

### Защита

- **Path traversal:** `isSafePath` проверяет, что путь внутри `-conf-dir`.
- **Расширение:** только `.conf`. `audit.log`, `users.json`, `templates.json`
  нельзя удалить этим эндпоинтом.
- **dnsmasq --test НЕ запускается** — удаление файла для dnsmasq
  эквивалентно «просто не загружать этот конфиг», проверять нечего.
  Активация изменений — через обычную кнопку «Применить».

## 2. Сброс rate-limit при успешном логине

Раньше: лимитер на `/api/login` считал **все** попытки с IP, включая
финальную успешную. Если пользователь опечатался 2 раза и вошёл с 3-й,
его IP оставался в счётчике ещё на минуту — следующий логаут-логин
мог упереться в `429 too_many_attempts`.

Теперь: при успешной проверке пароля счётчик для этого IP очищается
через `rateLimitReset(c.ClientIP())`.

### Что это меняет

- **Легитимный пользователь:** после опечаток сразу получает чистый
  счётчик. UX без «странных» 429 после корректного входа.
- **Брутфорс:** защита **не ослаблена**. Каждая неудачная попытка всё
  так же инкрементирует счётчик; после `maxAttempts` (10/мин) IP
  блокируется. Сброс происходит **только** при успешной аутентификации —
  то есть атакующий, не знающий пароля, никогда не получит сброс.

### API

Контракт `POST /api/login` не изменился. Новое поведение прозрачно
для клиентов.

## 3. Подсветка в UI: lease→static НЕ запускает `dnsmasq --test`

Массовое добавление аренд в статику (`POST /api/leases/to-static`) пишет
dhcp-host строки напрямую в файл, без прелиминарной валидации через
`dnsmasq --test`. Это сознательное решение — типичный сценарий «подключил
5 новых устройств, хочу их всех в статику за один клик» не должен
платить 5+ секундами bcrypt-подобных проверок. **Но пользователь должен
понимать, что изменения вступят в силу только после ручного нажатия
«Применить».**

### Что появилось в UI

- **Жёлтый alert-баннер** над таблицей аренд во вкладках «🔍 Обнаружение»
  и «Аренды», когда выделено хотя бы одно устройство. Текст (RU):
  *«Массовое добавление в статику пишет dhcp-host строки без проверки
  dnsmasq --test. После добавления нажмите «Применить» для активации.»*
- **В success-alert** после успешной конвертации добавлена явная строка:
  *«⚠️ dnsmasq --test НЕ запускался. Нажмите «Применить», чтобы
  активировать изменения.»* — на случай, если пользователь закрыл
  warning-баннер до выделения.

### Что НЕ изменилось

- Сам эндпоинт `POST /api/leases/to-static` — без изменений.
- Одиничное добавление через «➕ В статику» (copy-to-static flow) —
  пользователь видит предзаполненную форму и нажимает «Добавить»,
  обычный `addHostHandler` с валидацией.

## 4. Защита `users.json` от гонок

Добавлен пакетный `usersMu sync.RWMutex`, который удерживается на
протяжении всей последовательности read→modify→saveUsers() при
создании/удалении пользователей и смене пароля.

### Зачем это надо

Глобальный `mu sync.Mutex` в `main.go` сериализовал **запись**, но:

1. **`len(users)` в `statusHandler`** читал map без блокировки.
   Параллельный `POST /api/users` мог в этот момент писать → Go runtime
   падает с `fatal error: concurrent map read and map write` без stack
   recovery. В тесте `TestStatusHandlerSafeUnderConcurrentUserWrite` это
   воспроизводится на 50 горутинах за пару секунд.
2. **`saveUsers()` не атомарна относительно map** — две одновременных
   транзакции `POST /api/users` (разные username'ы) могли интерливиться:
   оба читают map → оба мутируют → оба пишут → один из новых пользователей
   теряется. Atomic write (`tmp + rename`) защищал от partial writes, но
   не от логичных гонок.

### Что теперь

- `usersMu.Lock()` удерживается во время:
  - проверки существования username,
  - хеширования пароля (bcrypt),
  - записи в map,
  - сохранения на диск.
- `usersMu.RLock()` берётся при чтении (`statusHandler`, `loginHandler`,
  `getUsersHandler`).
- При ошибке `saveUsers()` in-memory изменение откатывается — нет
  «призрачных» пользователей, которые есть в map, но отсутствуют на диске.

### Что НЕ изменилось

- Глобальный `mu` остаётся для сериализации операций с `.conf`-файлами.
- Файл `users.json` по-прежнему пишется atomically (tmp + rename),
  partial writes невозможны.

### Покрытие тестами

- `TestConcurrentCreateUserNoLostRecords` — 30 горутин одновременно
  создают разных пользователей; все 30 должны сохраниться.
- `TestConcurrentCreateUserDuplicateNoCorruption` — 20 горутин создают
  одного и того же пользователя; ровно один `200`, остальные `409 user_exists`.
- `TestStatusHandlerSafeUnderConcurrentUserWrite` — 50 writers + 50
  readers; без `usersMu` роняет процесс. Проверено с `go test -race`.

## 5. Рефакторинг: разбиение трёх больших файлов

Без изменения функциональности — только организация кода по доменам.

### Backend

| Файл (было) | Стало | Что внутри |
|---|---|---|
| `dnsmasq.go` (1543 строки) | 414 строк | Только ядро dhcp-host: парсинг, валидация, поиск, IP-transform, raw file IO |
| ↑ | `aliases.go` (~270) | DNS aliases (A/CNAME/PTR/TXT) |
| ↑ | `config_snapshot.go` (~310) | Визуальный редактор директив dnsmasq |
| ↑ | `arp_leases.go` (~110) | ARP, leases, обнаружение устройств |
| ↑ | `history.go` (~310) | Versioned history + `.bak` rollback + unified diff |
| ↑ | `backup.go` (~150) | ZIP backup/restore + удаление файлов |
| ↑ | `sse.go` (~125) | SSE broker + статус/reload dnsmasq |
| `handlers.go` (1534 строки) | 248 строк | Root: status, setup, login, reload, leases, events, bulk-lease-to-static |
| ↑ | `handlers_hosts.go` (~530) | CRUD хостов + bulk + CSV + templates |
| ↑ | `handlers_aliases.go` (~270) | CRUD DNS aliases + CSV |
| ↑ | `handlers_config.go` (~230) | Config editor + raw files + file delete (новый) |
| ↑ | `handlers_safety.go` (~170) | History + rollback + ZIP backup |
| ↑ | `handlers_users.go` (~145) | Users + logout |

### Frontend

| Файл (было) | Стало | Что внутри |
|---|---|---|
| `store.js` (451 строка) | 175 строк | Reactive state + axios + core actions (auth, status, SSE) |
| ↑ | `api/hosts.js` (~105) | Templates, bulk-move/edit, CSV, leases, new devices |
| ↑ | `api/dns.js` (~85) | DNS aliases CRUD |
| ↑ | `api/config.js` (~140) | Config editor + file delete + versioned history |
| ↑ | `api/system.js` (~105) | Backup/restore, audit, users, logout |

### Принципы разбиения

1. **`package main` сохранён.** Все файлы в том же пакете, импортов между
   ними нет, видимость функций не меняется. Сборка идентична.
2. **Именование по домену.** По имени файла сразу понятно, где искать
   код: `aliases.go` → DNS aliases, `handlers_hosts.go` → HTTP для хостов.
3. **Тесты не тронуты.** `dnsmasq_test.go` остаётся одним файлом на 2.4k
   строк — для тестов монолит лучше (легче `go test -run Test…`).
4. **Header-комментарий в каждом новом файле** объясняет его роль и
   указывает на родственные файлы — навигация без grep.

## Новые audit-actions

В Audit-вкладке появились цветные метки для ранее безымянных действий:

| Action | Цвет | Локализация |
|---|---|---|
| `config_delete_file` | красный | «Удаление файла» / «File deleted» |
| `config_write_raw` | синий | «Ручное редактирование файла» / «Raw file edit» |
| `user_create` | серый | «Создание пользователя» / «User created» |
| `user_delete` | серый | «Удаление пользователя» / «User deleted» |
| `password_change` | серый | «Смена пароля» / «Password change» |
| `bulk_lease_to_static` | серый | «Перенос аренд в статику» / «Lease to static» |
| `backup_restore` | синий | «Восстановление из ZIP» / «Backup restored» |

Раньше все они попадали в дефолтный серый «unknown».

## Совместимость

- **API:** все существующие эндпоинты, request/response форматы и коды
  ошибок сохранены. Единственное дополнение — `DELETE /api/config/file`.
- **Конфиг-файлы dnsmasq:** формат не меняется.
- **users.json:** формат не меняется.
- **Audit log:** набор `Action` значений расширен (см. таблицу выше),
  новые записи читаются старой версией UI как «неизвестное действие» —
  fallback корректный.
- **INTERMASQ_SECRET:** без изменений.
- **Флаги запуска:** без изменений.
- **JWT/blacklist:** без изменений. In-memory blacklist по-прежнему
  сбрасывается при рестарте (см. `docs/new-features.md §8`).

## Миграция

Не требуется. Обновление — заменить бинарник и собранный фронтенд.
Запускать миграции БД, перегенерировать секреты или править конфиги не
нужно.

## Известные ограничения (перенесены из v3.0)

- Глобальный `mu sync.Mutex` для `.conf`-файлов — узкое место при
  высокой нагрузке, для HomeLab-нагрузки (1-2 админа) неактуально.
- Метрики `*_total` — gauge, не настоящий Prometheus counter
  (`promauto`). В планах на рефакторинг.
- JWT blacklist in-memory — при рестарте процесса отозванные токены
  снова валидны до `exp` (72ч).
- Rate-limit cleanup — ленивый (срабатывает раз в 5 минут внутри
  middleware), фоновой горутины нет.
